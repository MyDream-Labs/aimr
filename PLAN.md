# План: управление IDE через MCP

Цель — расширить проверенную связку Codex → штатный MCP Theia → службы IDE, сохранив минимум собственного кода. Реализация завершена: четыре инструмента, пагинация и метаданные; DI и live smoke проверены. Покрытие и открытые вопросы — в `docs/ide-control-coverage.md`.

## 1. Понятная идентичность сервера

- ID подключения: `ide`.
- Название: `IDE Control — AIMR`.
- Описание: `Inspect and control the running AIMR IDE: settings, commands, extensions, panels and tabs.`
- Инструкции агента: `Use this server to inspect or change the running IDE. Search settings and commands before using unfamiliar IDs. Inspect current state before changing it and verify the result afterward. Tools operate on this IDE instance, not the operating system. Some operations may require a native confirmation or reload.`
- Инструменты: `ide_settings`, `ide_commands`, `ide_extensions`, `ide_layout`. Названия и описания операций — на английском, с понятными параметрами и результатами.
- Передавать инструкции через штатное MCP-поле `instructions`; назначение сервера также указать в описаниях инструментов. Проверить, какие метаданные действительно видит Codex: одного отображаемого названия недостаточно.

## 2. Четыре тонкие contribution

| Инструмент | Операции | Штатная основа |
| --- | --- | --- |
| `ide_settings` | `search`, `get`, `set`, `reset` | `PreferenceSchemaService`, `PreferenceService` |
| `ide_commands` | `search`, `run` | `CommandRegistry` |
| `ide_extensions` | `search`, `list`, `install`, `uninstall`, `enable`, `disable` | Registry service, `VSXExtensionsModel`, `VSXExtension` |
| `ide_layout` | `inspect`, `activate`, `show`, `hide`, `move`, `pin`, `unpin`, `close` | `ApplicationShell`, штатные команды |

- Каталоги настроек и команд читать из Theia, включая добавленные расширениями. Поиск возвращает ограниченную выборку; полные схемы и значения — по запросу.
- Для поиска и списков: `query`, `limit` (по умолчанию 20, максимум 100), `offset` (по умолчанию 0); ответ — `items`, `hasMore`, `nextOffset`, а `total` — если доступен у источника. Параметры — целые неотрицательные числа, `limit` не меньше 1.
- Настройки и команды фильтровать, сортировать по ID, затем применять пагинацию. При изменении `query` начинать с `offset: 0`. Поиск расширений адаптировать к штатной пагинации реестра; курсоры пока не вводить.
- Настройки: использовать существующие JSON-схемы для проверки значений и допустимых scope. Начать с User/Workspace; Folder и языковые переопределения отметить в покрытии. `reset` отделить от записи JSON `null`.
- Команды: возвращать ID, название и доступность. Общих схем аргументов у Theia нет; интерактивные и контекстные команды не считать автоматически проверенными.
- Расширения: сохранять штатные проверки, подтверждения и обработку перезагрузки. Возвращать фактический результат, включая отмену. Встроенные расширения продукта не удалять.
- Раскладка: возвращать компактное состояние с ID вкладок/панелей; проверять результат изменений. Геометрию внешнего окна пока не включать.
- Не дублировать файловые и системные инструменты Codex. Выполнение команды не означает управление произвольным внутренним API Theia.

## 3. Файл покрытия

Создать `docs/ide-control-coverage.md` и поддерживать рядом с реализацией.

Для каждой группы возможностей указать: операцию/конкретный command ID, штатный API, статус, ограничения и проверку. Статусы: **проверено**, **доступно, не проверено**, **требует обсуждения**, **вне текущего этапа**.

- Отдельно отметить: настройки и scope, команды без аргументов/с аргументами, контекстные команды, диалоги, расширения, раскладку, reload/restart и несколько окон.
- Доступность команды в каталоге не считать подтверждением её автоматизируемости. Все прочие команды реестра по умолчанию считать непроверенными.
- Полный актуальный список получать через `ide_commands.search`; не копировать тысячи команд в Markdown. В файл заносить проверенные сценарии и исключения, требующие решения.
- Добавить ссылки на файл из `docs/aimr-upstream.md` и `CONTRIBUTING.md`.

## 4. Реализация и совместимость

- KISS, YAGNI: минимум owned-кода и новых сущностей. Переиспользовать готовое; добавлять только необходимое для текущих сценариев, без абстракций, зависимостей и инфраструктуры «на будущее».
- Развивать отдельные файлы `theia-extensions/aimr-product/src`; существующие модули менять только для DI-регистрации.
- Использовать штатный MCP-сервер, frontend/backend-мост, публичные службы и небольшие DI-адаптеры. Без правок ядра, копирования сервисов и собственного транспорта.
- Схему и описание каждого инструмента объявлять один раз. Общий helper вводить только для реального повторения; без отдельного фреймворка.
- Пересмотреть текущее предодобрение двух тестовых инструментов перед расширением возможностей; сохранить штатные подтверждения Theia.
- Пока поддерживать одного MCP-клиента. Несколько окон/клиентов и замена временного transport override — отдельное решение, отражённое в покрытии.
- Обновлять карту `docs/aimr-upstream.md`, указывая привязки и причины переопределений.

## 5. Порядок и минимальные проверки

1. Идентичность сервера, метаданные и обобщённые настройки.
2. Поиск/выполнение команд.
3. Управление расширениями.
4. Управление панелями/вкладками.

Расширять существующие smoke-тесты: DI-регистрация contribution/адаптеров и видимые MCP-метаданные; чтение/изменение/сброс настройки; установка/удаление тестового VSIX; обратимое изменение панели и безопасная команда. Проверить соседние и пустую последнюю страницу, ограничения `limit`/`offset`. Живые проверки выполнять во временном профиле, восстанавливать изменённое состояние. Проверять повторное подключение.

После реализации — lint, тесты, сборка обычного Electron и перезапуск. Проверить из чистого контекста Codex, что он понимает назначение сервера и выбирает нужный инструмент. Коммит — по просьбе или перед отдельной новой задачей.
